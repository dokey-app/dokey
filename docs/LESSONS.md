- Абзац отрендерился заголовком H2, а строка таблицы — текстом -> правка документа скриптом (`sed Nc\`, удаление строк по номерам) съела пустую строку-разделитель, и в исходнике это не видно -> markdown правится с проверкой соседних строк, а структура документов держится тестом `tests/unit/docs-structure.test.ts` (RUN-01)
- G-02 показал `OK … 0 B` на странице со скриптом в 6,5 KB, а список шрифтов, собранный наполовину, мерился бы за целый -> разбор HTML и JS регуляркой по белому списку (`[^>]*`, `[\w$\s{},*]`) и глоб по семейству: всё, что не узнано, выпадает из счёта молча, а не валит гейт -> гейт разбирает по грамматике конструкции, а не по тому, что обычно выдаёт сборщик, у каждого разбора есть юнит-тест с краевыми формами (`tests/unit/size-gate.test.ts`), а предмет бюджета перечисляется явно и сверяется целиком
- После первой правки G-02 всё ещё терял скрипт за `<meta content="Кодирует тег <script>">` и валил правильную сборку на `x==="export"` -> регулярка искала `<script` и `import` по сырому тексту, не зная, где в HTML значение атрибута, а в JS — строка; первая правка закрыла найденные формы, а не класс -> разбор держит контекст токенизатора (чужой тег поглощается целиком, у ключевого слова проверяются сосед слева и то, что грамматика допускает справа), а разбор гоняется на враждебном вводе с замером времени
- G-02 висел минутами на файле с пятью строками обычного комментария `// … import …` -> альтернатива внутри повторяемой группы совпадала с одним текстом несколькими способами (`\/\/[^\r\n]*` кончался посреди строки и отдавал остаток имени и пробелу), и число разборов перемножалось с каждой строкой; тест на скорость гонял ввод без комментариев -> каждая альтернатива под `*` совпадает с текстом одним способом (разные первые символы, жёсткий конец), а тест на скорость содержит каждую альтернативу группы — комментарии, строки, имена
- G-02 молча потерял `import './polyfill.js'` без `;` после комментария со словом `import` и валил сборку на закомментированном импорте в классическом скрипте -> клауза брала имена по символу и перешагивала следующее объявление, проглатывая его спецификатор как строковое имя, а импорты искались и там, где их не бывает, — в классическом скрипте -> токен разбора — целое слово, и ключевые слова, начинающие новое объявление, в клаузу не входят; разбор применяется только к тому, что исполняется как модуль; разборщик сверяется с настоящим лексером (`es-module-lexer`) на `node_modules`, а не только на своих примерах
- G-02 ложно валил правильную сборку на `// import { debug } from './debug.js'`, на `@example` в JSDoc и на примере кода в шаблонной строке, а каждая правка регулярки открывала новый класс ошибок — пять прогонов /check подряд -> JS разбирался регуляркой, которая не знает, где в нём комментарий, строка или регулярное выражение -> язык с контекстом разбирается лексером своего инструментария (`es-module-lexer`, лексер Vite, D-158), регулярка — только для фиксированной грамматики; после второго класса ошибок в самописном разборщике ставится вопрос о настоящем парсере, а не третья заплатка
- G-02 показал `OK 73 B` на модуле, который браузер грузит на 2039 B, — файл сохранён как UTF-8 с BOM, и первый импорт пропал -> `readFile(…, 'utf8')` оставляет U+FEFF, а лексер читает `BOM + import` как имя; браузер BOM снимает при декодировании -> гейт читает файл так же, как его декодирует потребитель (браузер): ведущий BOM снимается до разбора, а тесты разборщика включают кодировочные края — BOM, CRLF, разделители строк
- `pnpm format:check` красный на чистом дереве: две таблицы в `src/README.md` и `scripts/gates/README.md` не выровнены -> 63ab142 дописал текст в ячейки руками и не прогнал Prettier, а CI (`pr.yml`), где `format:check` стоит, до T-002 не исполняется — локальный коммит ничем не проверялся -> после правки markdown вне `docs/` — `pnpm format` по затронутым файлам до коммита; CI проверяет только то, что дошло до PR, поэтому коммит в стопке локальных веток проходит чек-лист PR-шаблона (`lint && format:check && typecheck`) локально целиком, а не по «затронутым уровням»
- `gate:headers-parity` печатал «частные правила заменяют заголовки /*» на `_headers` без правила `/*` -> `concatenated()` при отсутствии предмета сравнения возвращала `[]`, то есть тот же ответ, что и «проблем нет», а гейт склеивал вывод из `problems.length === 0` -> ранний выход проверки, у которой не нашёлся предмет, возвращает проблему (или `pending`), а не пустой список; у каждой подпроверки гейта — юнит-тест на отсутствие предмета (`tests/unit/headers-parity.test.ts`)
- `gate:headers-parity` был зелёным, когда CSP стояла только в блоке `/sw.js` `_headers`, а остальные страницы шли без неё -> `fromHeadersFile()` брал первую строку с нужным именем в любом правиле, не зная, к какому пути она относится; nginx же ставит набор один раз на весь `server` -> разбор конфигурации с областями действия (правило, `location`, блок) держит область и сверяет значения только той, что покрывает все пути; заголовок сверяемого набора, заданный или снятый (одиночное `! Name` без повторной установки) в частной области, — отдельная проблема, и на оба случая есть юнит-тест (`tests/unit/headers-parity.test.ts`, T-242)
- `gate:headers-parity` был зелёным, когда CSP стояла только в `location = /sw.js` `nginx.conf`, а `add_header` в любом `location` снимал с его путей весь набор уровня server -> `fromNginxConf()` искал `add_header` регуляркой по всему файлу, не зная блока; T-242 закрыл ту же ошибку только в `_headers`, а вторую копию, разбираемую тем же способом, не проверил -> исправление разбора с областями действия применяется ко всем разборщикам того же гейта в одном заходе; для nginx блок директивы определяется разбором с учётом `{}`, `#` и кавычек, значения берутся только с уровня `server`, а любой `add_header` во вложенном блоке — проблема (`tests/unit/headers-parity.test.ts`, T-243)
- RUN-03 молчал после `$ playwright test` до отмены через 6 ч на каждом прогоне pr.yml, а локально был зелёным -> `globalSetup` звал `astro preview` через `spawnSync` в расчёте, что Astro 7 сам уйдёт в фон, но Astro уходит в фон, только если узнал агента по окружению (`am-i-vibing`: `CLAUDECODE` и т. п.); на раннере агента нет, сервер оставался на переднем плане, и `spawnSync` ждал его выхода вечно, а у job не было `timeout-minutes` -> поведение, которое инструмент выбирает по окружению, задаётся явным флагом (`astro preview --background`), у каждого синхронного вызова внешней команды — `timeout`, у каждого job — `timeout-minutes`; тест, зелёный у агента, воспроизводится и без переменных агента перед тем, как считать CI-падение «чужим» (T-228)
- Пять job'ов `pr.yml` остались без `timeout-minutes` после того, как T-228 закрыл ту же дыру у `e2e`: любое зависание держало бы раннер 6 ч, как RUN-03 до исправления -> потолок ставился в job, где зависание уже случилось, а не во все job'ы того же файла, и ничто не мешало завести следующий job без потолка — умолчание GitHub невидимо и молчит ровно до шестого часа -> настройка, защищающая от зависания или утечки ресурса, применяется ко всем однотипным единицам файла в один заход, значение обосновывается худшим зелёным прогоном из истории (`gh api .../jobs`), а не круглым числом, и держится машинной проверкой — `tests/unit/workflow-timeouts.test.ts` (RUN-01) валит новый job без `timeout-minutes`; сама проверка разбирает фиксированную грамматику регуляркой, поэтому строка уровня ключей job, не подошедшая под неё (`"build":`, `2fa:`), обязана быть проблемой, а не пропуском — иначе непонятый job наследует потолок соседа сверху и проходит молча, — а ожидания разбора сверены с настоящим js-yaml на тех же входах (T-244)
