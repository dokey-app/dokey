# Доступ к учётным записям и секретам (T-215, TECH-01)

Рунбук к **D-162**: как устроен доступ мейнтейнера к четырём учётным записям и к двум секретам
автоматики, как их ротировать и как восстановить доступ. Реестр секретов с правилами —
[security-and-access §5.3](../../docs/security-and-access.md#53-управление-секретами), приёмка —
ЧЛ-92 [launch-checklist](../../docs/launch-checklist.md).

Логинов, резервных кодов, ключей, имени доверенного лица и места хранения набора восстановления
здесь нет и не будет (**D-162** п. 5, SEC-15). В репозитории — только факт и порядок.

## Что должно быть

1. Четыре учётные записи мейнтейнера (ROLE-03) — GitHub-организация, Cloudflare, регистратор,
   провайдер VPS — защищены вторым фактором TOTP или passkey; **SMS не используется** (SEC-11).
2. Резервные коды каждой записи хранятся офлайн и не на том устройстве, где стоит второй фактор.
3. **Второго владельца с постоянными правами нет** ни в одной из четырёх (THR-02, THR-03).
   Вместо него у доверенного лица есть отложенный аварийный доступ к набору восстановления —
   резервным кодам и ключам всех четырёх записей (**D-162** п. 5).
4. Секретов автоматики два — токен деплоя Cloudflare и секрет плеча (**D-162** п. 1). У обоих срок
   ротации 6 месяцев, меняются они в один приход.
5. Токен деплоя живёт только в environment `production` репозитория, а это environment
   принимает развёртывания только с тегов `v*` (**D-162** п. 3).

## Учётные записи

| Учётная запись                  | Второй фактор | Резервные коды | Что даёт при утрате                                                    |
| ------------------------------- | ------------- | -------------- | ---------------------------------------------------------------------- |
| GitHub, организация `dokey-app` | TOTP          | офлайн         | Код, гейты, секреты Actions, публикация образа, деплой                 |
| Cloudflare                      | TOTP          | офлайн         | Прод `dokey.ru`, зона DNS, Email Routing                               |
| Регистратор REG.RU              | TOTP          | офлайн         | Домен — отказ без обходного пути (ИНТ-09); подробности — `infra/dns/`  |
| Провайдер VPS                   | TOTP          | офлайн         | Оплата и консоль VPS приёмника; SSH-ключ (SEC-09) — отдельный носитель |

В организации GitHub включено «Require two-factor authentication» (T-002): участник без второго
фактора исключается платформой. Сверка остальных трёх — ручная, раз в квартал (ниже).

### Восстановление при потере второго фактора

Мейнтейнер сам, в порядке от самого дорогого к самому дешёвому отказу:

1. **Регистратор.** Вход резервным кодом, затем новый TOTP. Без кодов — через поддержку
   регистратора с подтверждением личности администратора домена. Пока доступ не восстановлен,
   сверить, что автопродление и запрет смены регистратора включены (SEC-12), — по письмам
   регистратора.
2. **Cloudflare.** Вход резервным кодом, затем новый TOTP. Без кодов — через поддержку
   Cloudflare. Токен деплоя живёт своим сроком и прод не останавливает; при подозрении на
   компрометацию — порядок «при утечке» ниже.
3. **GitHub.** Вход резервным кодом, затем новый TOTP. Без кодов — Account recovery GitHub
   (подтверждение по SSH-ключу или устройству, занимает дни). Владелец организации один, поэтому
   до восстановления организацией не управляет никто — релизы стоят, прод и образ продолжают
   работать.
4. **Провайдер VPS.** Вход резервным кодом, затем новый TOTP. Без кодов — через поддержку
   провайдера. SSH-доступ к самой машине от учётной записи не зависит; следить, чтобы VPS не
   отключили за неоплату.

После каждого восстановления: выпустить новые резервные коды, старые уничтожить, обновить набор
восстановления у доверенного лица, записать дату в журнал.

### Выбытие мейнтейнера

Порядок для доверенного лица (**D-162** п. 5). Частичного отзыва нет: любая из четырёх записей
даёт контроль над тем, что исполняется у пользователя, поэтому они передаются только вместе
(security-and-access §1, ROLE-03).

1. Запросить аварийный доступ к набору восстановления — через механизм, заведённый вне
   репозитория, и дождаться окончания задержки. Задержка — это защита, а не помеха: у
   мейнтейнера есть время отклонить ошибочный запрос.
2. **Первым — регистратор:** проверить дату истечения `dokey.ru` и автопродление. Потеря домена
   необратима для всех сохранённых ярлыков и установленных PWA (ИНТ-09).
3. **Вторым — Cloudflare:** прод работает без вмешательства; ничего не деплоить руками (SEC-19).
4. **Третьим — GitHub:** не выпускать релизы и не сливать PR, пока не решено, кто продолжает
   проект. Прод трогает только конвейер, и конвейер без тега ничего не делает.
5. **Четвёртым — провайдер VPS:** продлить оплату, если она истекает; приёмник на пользователей
   не влияет (NFR-11), его отказ допустим.
6. Передать все четыре записи новому мейнтейнеру целиком, после чего он выпускает новые резервные
   коды, ротирует оба секрета и заводит свой отложенный доступ.

## Секреты автоматики

| Секрет                                | Где живёт                                                                        | Кто выпускает            | Срок      |
| ------------------------------------- | -------------------------------------------------------------------------------- | ------------------------ | --------- |
| `CLOUDFLARE_API_TOKEN` — токен деплоя | Секреты environment `production`, `dokey-app/dokey`; на устройство не копируется | Мейнтейнер, T-011        | 6 месяцев |
| Секрет плеча до приёмника             | Конфигурация Worker'а и конфигурация TLS-фронта VPS; в браузер не попадает       | Мейнтейнер, T-026, T-027 | 6 месяцев |

`CLOUDFLARE_ACCOUNT_ID` лежит рядом с токеном, но секретом не является: это идентификатор, без
токена он ничего не даёт, поэтому в реестре §5.3 его нет.

### Ротация токена деплоя

Раз в 6 месяцев; секрет плеча — в тот же приход. Пропуск ротации не проходит тихо: у токена срок
задан в самом Cloudflare, и просроченный токен даёт красный релиз (**D-43**).

1. Cloudflare → My Profile → API Tokens → Create Token → Custom token.
2. Permissions: **Account · Workers Scripts · Edit** — единственная строка. Account Resources:
   Include — только аккаунт проекта. Client IP filtering — не задаётся: адреса раннеров GitHub
   не фиксированы.
3. TTL: начало — сегодня, окончание — **не позже чем через 6 месяцев**.
4. Записать токен сразу в environment, минуя файлы и историю shell — `gh` прочитает значение из
   приглашения:

   ```bash
   gh secret set CLOUDFLARE_API_TOKEN --env production -R dokey-app/dokey
   ```

5. Удалить прежний токен в Cloudflare → API Tokens. Токен выпускается новый, а не перевыпускается
   прежний: так срок и право задаются заново и сверяются глазами.
6. Проверить ближайшим релизом: задание «Прод» зелёное. Отдельный тег ради проверки не ставится —
   он публикует образ.
7. Записать даты в журнал ниже.

### Ротация секрета плеча

Появится с T-026 (фронт VPS) и T-027 (отправка Worker'ом); порядок — после них, в этом файле.
Принцип: новое значение генерируется локально и сразу записывается в обе конфигурации одним
приходом; события, отклонённые в промежутке, — допустимая потеря аналитики (NFR-11). Проверка —
запрос с адреса Cloudflare без секрета получает отказ (SEC-10, **D-147** п. 4).

### При утечке

Порядок — в строке секрета реестра
[§5.3](../../docs/security-and-access.md#53-управление-секретами): отозвать, выпустить новый,
проверить журнал деплоев за период, для токена — пересобрать и передеплоить прод.

## Environment `production`

Задание «Прод» в [release.yml](../../.github/workflows/release.yml) объявляет
`environment: production`, и только оно получает токен. Environment принимает развёртывания по
правилу «Selected branches and tags» с единственным правилом — тег `v*`. Прогон из PR, с `main`
или из форка (SEC-17) секрета не получает. Рецензентов нет: второго человека нет (**D-162** п. 5).

## Как проверить

```bash
# environment: только теги v*
gh api repos/dokey-app/dokey/environments/production --jq '.deployment_branch_policy'
gh api repos/dokey-app/dokey/environments/production/deployment-branch-policies \
  --jq '.branch_policies[] | [.name, .type]'          # ровно ["v*","tag"]

# организация требует второй фактор
gh api orgs/dokey-app --jq '.two_factor_requirement_enabled'   # true

# секрет есть только в environment, а не на уровне репозитория (после T-011)
gh secret list -R dokey-app/dokey --env production    # CLOUDFLARE_API_TOKEN
gh secret list -R dokey-app/dokey                     # без CLOUDFLARE_API_TOKEN
```

Срок и право токена видны только в Cloudflare → API Tokens: строка токена показывает
`Workers Scripts:Edit` и дату окончания не дальше 6 месяцев от выпуска.
